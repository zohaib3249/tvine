200 connections from 4 load processes on the same 8 cores. Tvine runs tvine start --workers 8 with sessions and rate limits shared on Redis; that Redis bookkeeping (about 19 calls per request) is its limit here, the next speed task.

The client sends at a fixed rate; a step fails when p99 goes over the dashed line or more than 1% of requests fail (red dots). 100,000 a second was not reachable here: the load processes ran out of CPU first.

A real visitor during a 30-second flood

While the flood runs, a separate visitor on another IP asks for a page five times a second. The bar is the share of the visitor's requests that were answered.

A flood from one IP is turned away by the per-IP limit, which costs far less than serving it, so the visitor keeps getting pages. A flood spread over 1,000 IPs keeps each IP under the limit, so the single process fills up and the visitor's connections are reset. Stopping that needs a whole-site emergency mode and more processes.

Where Tvine's time goes

Share of busy CPU, one process reading one row under load

From a CPU profile. The rate limiter is busy even with the limit lifted, because every anonymous request gets a new throwaway session; SQL statements are compiled again on every query. Both are fixable. The HTTP middleware is a small share.

How it was measured

  • Everything ran on one laptop, so the load tool and the servers share the same cores. Read the numbers as this machine's limits, not a production ceiling.
  • SQLite rather than Postgres; Redis on the same machine.
  • Tvine ran as a full app with Next.js and security headers in the same process. Express, FastAPI and raw Node ran with no security middleware.
  • The scale, eight-process, MCP and flood results are single runs.
  • The code and the raw results: benchmarks/ in the Tvine repository. ./run.sh reruns everything; node report.mjs rebuilds this page.
